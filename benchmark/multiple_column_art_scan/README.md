# Multiple-column ART scan benchmark

This directory contains the SQL setup, CLI diagnostic runner, and native steady-state runner used by
`REPORT.md`. Build the baseline and patched binaries from the same source revision, and run each binary
against its own copy of the database. The native runner opens one DuckDB instance and creates the requested
number of connections in that process.

## Setup and CLI diagnostics

```sh
CPU_SET=48-64 benchmark/multiple_column_art_scan/run.sh \
  /path/to/build/duckdb /tmp/mca-baseline B
```

`run.sh` creates `/tmp/mca-baseline/orders.db` from `setup.sql`, records the plan, and runs the CLI
diagnostic workload with index scans enabled and disabled. The setup contains one million `orders` rows
with a primary-key ART on `id`, plus a 10,000-row `candidate_orders` table with 1,500 rows at
`lookup_key = 42` and a secondary ART on that column.

The guarded implementation keeps the existing candidate cap and, only for multi-filter scans, applies a
segment-level codec admission check. DICT_FSST and ZSTD use a conservative `1/32` candidate factor;
ordinary codecs keep factor `1`. The check reads only fetched columns and actual touched segment metadata.
This is a heuristic for known costly codecs; ordinary-codec Index Scan can still lose to Sequential Scan.
Use label `G` with the guarded Release build when comparing it with baseline `B` and the unguarded patch
`P`.

## Native steady-state runner

The runner is compiled against the selected build's shared library. The build directory must contain
`src/libduckdb.so` and its CMake-generated headers.

```sh
CPU_SET=48-64 benchmark/multiple_column_art_scan/native_run.sh \
  /path/to/build /tmp/mca-baseline/orders.db /tmp/mca-baseline/native B 1 8 5
```

The positional arguments after the output directory are `LABEL`, `THREADS`, `CONNECTIONS`, measurement
seconds, and optional scan mode (`default` or `seq`). `seq` sets both index thresholds to zero on every
connection, providing a Sequential Scan control from the same source. `THREADS` is configured once for the
DuckDB instance; `CONNECTIONS` is the number of application
threads, each owning one connection. The command writes one JSON result for each of `point`, `in32`, `wide`,
`medium_plain`, and `medium_zstd`. `point` cycles through
the keys generated by `(i * 48271) % 1000000` for `i = 12345..12374`; `in32` uses the same formula for
`i = 12345..12376`. Each connection warms up and passes a correctness gate before the measured interval.
The wrapper verifies every worker thread's affinity, and each JSON records the observed affinity,
user/system CPU seconds, and CPU/query (process user plus system CPU divided by completed queries).
`requested_seconds` records the target interval; `elapsed_s` includes queries started before the deadline
and completed after it, through the final worker join. QPS and the CPU/wall check use that actual elapsed time.

For the focused single-filter control, invoke the compiled runner directly with query `single`:

```sh
taskset -c 48-64 /path/to/output/native_runner /path/to/orders.db 1 8 single 5
```

This uses `SELECT count(*) FROM orders WHERE id = ?` with the same point keys. To isolate codec admission,
compare the full patch with a same-base build that disables only that guard, keeping the vacuum-lock
lifecycle and other changes identical. Use label `S` for the same-source `seq` control.

When JSON files from both builds are collected in one directory, the same checks and table source can be
run with:

```sh
python3 benchmark/multiple_column_art_scan/summarize_native.py /path/to/native-results
```

`medium_plain` measures 128 candidates in a 100,000-row uncompressed table; `medium_zstd` uses the same
candidate count and table size with ZSTD payload segments. These two queries set
`index_scan_max_count=2048` and `index_scan_percentage=0`, so the ZSTD admission cap is 64 candidates.
They provide focused admitted metadata-walk and guarded rejection cases without expanding the normal
thread/connection matrix.

Both medium tables initially place the 128 candidates at row IDs 0–127; non-candidate keys cycle through
0–40. To compare scattered access with the same logical rows, copy the setup database and run:

```sh
cp /path/to/orders.db /path/to/orders-scattered.db
/path/to/build/duckdb -bail /path/to/orders-scattered.db < benchmark/multiple_column_art_scan/scatter.sql
```

`scatter.sql` sorts the original rows by `(rowid * 71631) % 100000`, verifies both row multisets with
`EXCEPT ALL`, and recreates the same indexes and codecs. Use the existing `medium_plain` and `medium_zstd`
runner queries against each database. Check candidate row IDs and touched segments before timing: physical
order also changes segment composition and zonemaps. The original `in32` keys are numerically scattered,
but their physical row IDs are consecutive; that workload does not establish scattered Fetch performance.

Run the baseline and patch separately so that neither binary or database snapshot is shared:

```sh
CPU_SET=48-64 benchmark/multiple_column_art_scan/run.sh /path/to/build-B/duckdb /tmp/mca-B B
CPU_SET=48-64 benchmark/multiple_column_art_scan/run.sh /path/to/build-P/duckdb /tmp/mca-P P
CPU_SET=48-64 benchmark/multiple_column_art_scan/native_run.sh \
  /path/to/build-B /tmp/mca-B/orders.db /tmp/mca-B/native B 1 8 5
CPU_SET=48-64 benchmark/multiple_column_art_scan/native_run.sh \
  /path/to/build-P /tmp/mca-P/orders.db /tmp/mca-P/native P 1 8 5
CPU_SET=48-64 benchmark/multiple_column_art_scan/native_run.sh \
  /path/to/build-G /tmp/mca-P/orders.db /tmp/mca-G/native G 1 8 5
```
